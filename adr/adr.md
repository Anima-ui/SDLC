# Модульный монолит для серверной части «КиноНавигатора»

Идентификатор: ADR-001.

## Контекст и постановка задачи

«КиноНавигатор» объединяет доступ к учётной записи, каталог фильмов, приватную коллекцию и рекомендации. Сервер должен проверять владельца данных, атомарно изменять личные записи и сохранять доступность коллекции при отказе TMDB. Исходная Maven-заготовка использует Java 17.

Нужно выбрать организацию серверной части: одно приложение с внутренними модулями либо несколько самостоятельных сервисов. Оба варианта предполагают браузерную SPA и серверную обработку личных данных согласно SRS.

## Драйверы решения

* Простая локальная поставка и сборка Maven — REQ-INST-001, REQ-BUILD-001.
* Атомарное изменение записей и отсутствие дублей — REQ-REL-001, REQ-REL-004.
* Разделение доступа, каталога, коллекции и рекомендаций — REQ-MAINT-001.
* Замена TMDB заглушкой и тестирование рекомендаций без сети и БД — REQ-MAINT-002–003.
* Серверный контроль владельца данных — REQ-FUNC-005, REQ-SEC-002.

## Рассмотренные варианты

* Модульный монолит: одно Java-приложение, внутренние модули и общая реляционная БД.
* Микросервисы: отдельно запускаемые сервисы доступа, каталога, коллекции и рекомендаций с собственными данными.

## Итог решения

Выбран **модульный монолит**, потому что для текущего MVP важнее простая поставка и единая транзакция, чем независимое масштабирование функций. Разделение обязанностей сохраняется внутри приложения.

В сервере выделяются AuthService, CatalogService, CollectionService, RecommendationService и AdminService. Контроллеры обрабатывают HTTP, сервисы выполняют сценарии, репозитории сохраняют данные. Интерфейс MovieProvider скрывает TMDB; отказ внешнего API не должен блокировать локальные запросы. Правила рекомендаций не зависят от HTTP и БД.

Для реализации выбран Spring Boot на Java 17. Общая PostgreSQL позволяет задать уникальность пары пользователь–фильм и выполнить удаление аккаунта с личными записями одной транзакцией; изменения схемы оформляются миграциями Flyway. Статическая SPA поставляется тем же приложением, поэтому локальный запуск требует Java-сервер и БД.

### Последствия

* Одна серверная сборка и одна схема БД упрощают запуск и проверку MVP.
* Изменение коллекции и удаление аккаунта не требуют распределённых транзакций.
* Модули нельзя поставлять и масштабировать независимо; сбой процесса затрагивает весь сервер.
* Общая БД может связать модули слишком тесно. Работа с таблицами выполняется через сервисы и репозитории соответствующей области, а не из HTTP-контроллеров.

### Подтверждение

При реализации проверяются:

1. Сборка Maven создаёт один серверный артефакт со статическим клиентом.
2. Модули доступа, каталога, коллекции и рекомендаций имеют отдельные обязанности; в правилах рекомендаций нет HTTP- и SQL-вызовов.
3. Интеграционные тесты подтверждают откат изменения, отсутствие дублей и отказ в доступе к чужой записи.
4. При отключённом TMDB открываются коллекция и сохранённые карточки.

## Плюсы и минусы вариантов

| Критерий | Модульный монолит | Микросервисы |
|---|---|---|
| Локальный запуск | Один сервер и БД | Несколько сервисов и их конфигураций |
| Согласованность данных | Одна транзакция БД | Межсервисные операции требуют дополнительного согласования |
| Разделение обязанностей | Поддерживается границами модулей и ревью | Поддерживается границами сервисов и API |
| Масштабирование | Сервер масштабируется целиком | Сервисы масштабируются независимо |
| Отказ сервера | Может затронуть все функции | Может быть локализован в отдельном сервисе |
| Соответствие масштабу MVP | Достаточен для текущих сценариев | Эксплуатационная сложность пока не оправдана |

## Дополнительная информация

Основание — [SRS 0.2](../srs/srs.md). Решение раскрыто в [SDD](../sdd/sdd.md): DV-001 — границы системы, DV-002 — компоненты, DV-003 — общая модель данных, DV-005 — отказ TMDB, DV-007 — транзакции, DV-008 — поставка.

Решение следует пересмотреть, если измеренная нагрузка потребует отдельного масштабирования рекомендаций либо появится необходимость независимо поставлять модули.
