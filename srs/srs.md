## 1. Введение

### 1.1 Назначение документа

Документ определяет требования к веб-приложению «КиноНавигатор» для учёта просмотренных фильмов, ведения списка запланированных просмотров и получения персональных рекомендаций. Спецификация описывает, **что** должен предоставлять продукт, какие ограничения необходимо соблюдать и как будет проверяться результат.

Документ предназначен:

- заказчику — для проверки бизнес-целей, границ и приоритетов;
- менеджеру проекта — для оценки объёма, сроков и влияния изменений;
- разработчику — для проектирования и реализации веб-приложения на Java;
- тестировщику — для подготовки проверок по идентификаторам требований;
- ответственному за эксплуатацию — для понимания зависимостей, наблюдаемости и порядка развёртывания.

Спецификация является главным источником требований первого выпуска. Архитектурные решения, исходный код, тест-кейсы и инструкция развёртывания должны ссылаться на идентификаторы требований из этого документа.

### 1.2 Область применения продукта

«КиноНавигатор» — новое одностраничное веб-приложение, позволяющее пользователю вести личный журнал фильмов и получать объяснимые рекомендации. Продукт решает две связанные задачи: сохраняет историю просмотра в структурированном виде и сокращает время выбора следующего фильма.

В первый выпуск входят:

- регистрация, вход и управление личной учётной записью;
- поиск фильмов и просмотр карточки фильма;
- получение сведений о фильмах из TMDB либо резервного локального каталога;
- статусы «Хочу посмотреть», «Просмотрен» и «Брошен»;
- дата просмотра, персональная оценка и текстовая заметка;
- фильтрация и сортировка личной коллекции;
- персональная подборка на основе оценок, статусов и жанров;
- объяснение причины каждой рекомендации;
- экспорт собственных записей и удаление учётной записи;
- административное обновление локального каталога.

В первый выпуск не входят:

- воспроизведение фильмов и хранение видеоконтента;
- покупка билетов или подписок онлайн-кинотеатров;
- общение пользователей, комментарии и публичные профили;
- импорт из IMDb, «Кинопоиска» и других пользовательских аккаунтов;
- мобильное приложение для Android или iOS;
- автоматическое обучение модели машинного обучения;
- коммерческая эксплуатация.

Предполагаемые бизнес-результаты:

| ID | Бизнес-цель | Показатель достижения |
|---|---|---|
| BG-01 | Сосредоточить историю просмотра в одном сервисе | Пользователь находит сохранённую запись не более чем за три действия после входа |
| BG-02 | Сократить усилия при выборе фильма | Пользователь получает до 10 неповторяющихся непосмотренных предложений и может сохранить выбранное одним действием |
| BG-03 | Повысить доверие к рекомендациям | Каждая рекомендация содержит понятную причину, основанную на данных пользователя |
| BG-04 | Обеспечить контроль над личными данными | Пользователь может экспортировать записи и удалить учётную запись вместе с ними |
| BG-05 | Обеспечить устойчивость первого выпуска | Основные сценарии работают при недоступности внешнего каталога на резервном наборе данных |

## 2. Обзор продукта

### 2.1 Перспектива продукта

«КиноНавигатор» создаётся как самостоятельное клиент-серверное веб-приложение. Браузер обращается к серверу приложения по HTTPS. Сервер выполняет проверку прав, бизнес-логику, работу с личными записями и формирование рекомендаций. Реляционная база данных хранит учётные записи, локальный каталог, статусы и оценки.

TMDB рассматривается как внешний поставщик метаданных: названий, описаний, жанров, дат и путей к изображениям. Пользовательские оценки и заметки хранятся только в «КиноНавигаторе» и не отправляются в TMDB. Если внешний сервис временно недоступен, ранее синхронизированные карточки и личная коллекция остаются доступными.

Контекст системы:

```text
Пользователь ── HTTPS ──> КиноНавигатор ── SQL ──> база данных
                              │
                              └── HTTPS ──> TMDB API

Администратор ─ HTTPS ──> КиноНавигатор
```

Владелец продукта определяет приоритеты и принимает изменения требований. До выбора производственной среды формальное SLA не устанавливается. Публичный запуск потребует отдельного решения по размещению, мониторингу, резервному копированию и обработке персональных данных.

### 2.2 Функции продукта

#### Управление доступом

- регистрация по адресу электронной почты и паролю;
- вход и завершение сеанса;
- просмотр и изменение отображаемого имени;
- удаление своей учётной записи.

#### Каталог фильмов

- поиск по части названия;
- фильтрация по жанру и году;
- просмотр подробной карточки;
- получение и кэширование метаданных внешнего сервиса;
- резервный поиск по локальному каталогу.

#### Личная коллекция

- добавление фильма со статусом;
- указание даты, оценки и заметки;
- изменение и удаление записи;
- фильтрация по статусу;
- сортировка по названию, дате и оценке;
- экспорт в CSV.

#### Рекомендации

- исключение просмотренных и брошенных фильмов;
- ранжирование по совпадению жанров и оценкам;
- выдача общего набора при холодном старте;
- объяснение основания подбора;
- добавление рекомендации в список просмотра.

#### Администрирование

- просмотр состояния синхронизации каталога;
- создание и исправление локальной карточки;
- отключение недоступной или ошибочной карточки;
- запуск ручного обновления метаданных.

| ID | Ограничение | Тип |
|---|---|---|
| CON-01 | Продукт должен быть веб-приложением | Обязательное продуктовое ограничение |
| CON-02 | Серверная часть должна быть реализована на Java | Обязательное технологическое ограничение |
| CON-03 | Основной интерфейс первого выпуска должен быть русскоязычным | Обязательное |
| CON-04 | Внешние секреты, включая токен TMDB, не должны попадать в Git | Обязательное |
| CON-05 | Продукт не должен хранить и распространять видеофайлы | Обязательное |
| CON-06 | MVP не должен требовать платной лицензии или обязательного платного API | Бюджетное ограничение |
| CON-07 | Данные пользователя не должны использоваться для обучения общей модели | Обязательное для MVP |

| CON-09 | При недоступности TMDB личная коллекция должна оставаться доступной | Обязательное |

Предпочтительный стек, который может быть уточнён архитектурным решением: Java 21, Spring Boot, Spring Security, PostgreSQL, Maven, HTML/CSS/JavaScript либо отдельный веб-клиент. Эти технологии не должны менять наблюдаемое поведение, определённое требованиями.

### 2.4 Характеристики пользователей

| Роль | Опыт и доступ | Основные цели | Частота работы |
|---|---|---|---|
| Гость | Не авторизован, специальных знаний нет | Найти фильм, изучить возможности, зарегистрироваться | Эпизодически |
| Пользователь | Авторизован, обычная цифровая грамотность | Вести коллекцию, ставить оценки, выбирать фильм | Несколько раз в неделю |
| Новый пользователь | Авторизован, оценок пока нет | Быстро начать работу и получить первые предложения | Первые сеансы |
| Активный пользователь | Имеет десятки или сотни записей | Фильтровать историю и получать персональный подбор | Регулярно |
| Администратор каталога | Знает правила продукта и источник метаданных | Исправлять карточки и контролировать синхронизацию | По необходимости |
| Сопровождающий | Имеет технический доступ к журналам и конфигурации | Диагностировать ошибки без чтения личных заметок | При инцидентах |

Интерфейс не должен требовать понимания алгоритмов рекомендаций. Причина предложения формулируется обычным языком. Цвет не используется как единственный способ передать статус. Основные элементы доступны с клавиатуры и имеют текстовые подписи.

### 2.5 Допущения и зависимости

| ID | Допущение или зависимость | Влияние при нарушении | Мера снижения риска |

| DEP-04 | Заказчик подтвердит необходимость регистрации | Возможна переработка доступа и хранения | Обсудить до реализации авторизации |

### 2.6 Распределение требований

| Выпуск | Содержание | Включённые требования |
|---|---|---|
| Базовая спецификация | SRS и мокапы интерфейса | Требования согласованы владельцем продукта |

При ограничении сроков приоритет имеют: защита личных данных, поиск, создание личной записи, коллекция и базовые рекомендации. Административный интерфейс допускается заменить подготовленной процедурой импорта только после согласования заказчиком.

## 3. Требования

Термин «система должна» обозначает обязательное требование MVP. Каждый критерий приёмки проверяется независимо. Требования не описывают внутренний алгоритм, если он не является обязательным ограничением.

### 3.1 Внешние интерфейсы

#### 3.1.1 Пользовательские интерфейсы

##### Общая компоновка

После входа основная навигация должна содержать разделы «Каталог», «Моя коллекция», «Рекомендации» и меню профиля. Текущий раздел визуально обозначается и программно отмечается для вспомогательных технологий. На мобильной ширине навигация может сворачиваться в меню.

##### Экран каталога

Экран содержит строку поиска, фильтр жанра, фильтр года и список карточек. Карточка показывает название, год, жанры, общую оценку при её наличии и персональный статус. Пустая выдача содержит объяснение и действие сброса фильтров. Макет: [catalog.png](figures/mockups/catalog.png).

##### Карточка фильма

Экран содержит общие сведения, постер, описание и форму личной записи. Для просмотренного фильма доступны дата, оценка и заметка. Ошибки проверки отображаются рядом с соответствующими полями; введённые значения не исчезают после ошибки. Макет: [movie-details.png](figures/mockups/movie-details.png).

##### Экран рекомендаций

#### 3.1.2 Аппаратные интерфейсы

Специальное оборудование не требуется. Клиентское устройство должно предоставлять экран, клавиатуру или сенсорный ввод и сетевое соединение. Камера, микрофон, геолокация и аппаратные датчики не используются. Серверная конфигурация определяется нагрузочным профилем и не является частью пользовательского интерфейса.

#### 3.1.3 Программные интерфейсы

##### Клиентский API

Сервер предоставляет HTTP API с JSON-представлением. Предполагаемые группы ресурсов:

| Ресурс | Операции | Назначение |
|---|---|---|
| `/api/auth` | регистрация, вход, выход | Управление сеансом |
| `/api/movies` | поиск, фильтры, получение карточки | Общий каталог |
| `/api/collection` | чтение, создание, изменение, удаление | Личные записи |
| `/api/recommendations` | получение подборки | Персональные рекомендации |
| `/api/profile` | чтение, изменение, экспорт, удаление | Данные пользователя |
| `/api/admin/movies` | CRUD и синхронизация | Управление каталогом |

Конкретная схема API должна быть документирована в OpenAPI до реализации клиента. Ошибки возвращаются в едином формате: код, понятное сообщение и необязательное имя поля. Внутренняя трассировка не выдаётся пользователю.

##### TMDB API

Интеграция использует HTTPS и серверный токен. Базовый сценарий: поиск фильма, получение идентификатора и запрос подробностей. Токен хранится во внешней конфигурации. Система соблюдает требования атрибуции источника. Тайм-аут или ошибка внешнего сервиса не должны препятствовать чтению уже сохранённой коллекции.

##### База данных

Доступ к БД выполняется только серверной частью. Клиент не получает строку подключения. Миграции схемы версионируются вместе с приложением. Внешние идентификаторы фильмов не используются как единственный первичный ключ личной записи.

| REQ-COMP-005 | Перед публичным запуском должна быть проведена проверка применимых требований к персональным данным | Существует записанное решение владельца продукта | Инспекция |

Спецификация не заявляет юридическое соответствие без отдельной проверки юристом или уполномоченным лицом. В тестовой и демонстрационной средах используются вымышленные адреса и синтетические данные.

| REQ-MAINT-002 | Интеграция TMDB должна быть скрыта за внутренним интерфейсом поставщика каталога | Заглушка заменяет внешний клиент в тестах |

#### 3.5.5 Повторное использование

Модель фильма, контракт коллекции и сервис рекомендаций должны быть независимы от конкретной разметки веб-клиента. Это позволит создать мобильный клиент или командный интерфейс без изменения бизнес-правил. Код интеграции внешнего API не должен проникать в сущность личной записи.

| ID | Требование | Критерий |
|---|---|---|
| REQ-REUSE-001 | Внешняя и внутренняя модели фильма должны преобразовываться отдельным компонентом | Доменная модель не содержит типов библиотеки TMDB |
| REQ-REUSE-002 | Контракт API должен быть документирован независимо от клиента | OpenAPI-файл проходит проверку синтаксиса |

#### 3.5.6 Переносимость

| REQ-PORT-002 | Настройки окружения не должны содержать абсолютные пути разработчика | Поиск не обнаруживает обязательных путей `D:\...` или пользовательского профиля |
| REQ-PORT-003 | Клиент должен работать в двух последних стабильных основных версиях Chrome, Edge и Firefox на дату выпуска | Матрица браузерной проверки заполнена |

#### 3.5.7 Стоимость

Первый выпуск должен использовать инструменты с открытыми либо бесплатными для некоммерческого применения лицензиями. Обязательные платные сервисы запрещены. Переменные расходы публичного хостинга не входят в текущий бюджет продукта.

| ID | Требование | Критерий |
|---|---|---|
| REQ-COST-001 | MVP не должен требовать оплаты за сборку и локальную демонстрацию | Все обязательные компоненты запускаются без платежа |
| REQ-COST-002 | Коммерческое использование внешних данных требует отдельной оценки лицензии | В документации присутствует ограничение |

#### 3.5.8 Сроки

| Этап | Результат | Условие завершения |
|---|---|---|
| Согласование требований | SRS и PNG-мокапы | Документы прошли ревью владельца продукта |
| Проектирование | Архитектура, ADR, схема данных, API | Требования MVP распределены по компонентам |
| Реализация MVP | Работающие основные сценарии | REQ-FUNC-001–029 реализованы либо согласованно перенесены |
| Проверка | Отчёт тестов и демонстрация | Нет открытых критических дефектов |

Точные календарные даты определяются планом выпуска. Изменение объёма после согласования требует анализа влияния на срок поставки.

#### 3.5.9 Доказательство концепции

До полной реализации выполняются два ограниченных прототипа:

1. Интеграционный прототип: поиск фильма в TMDB, получение карточки и сохранение локальной копии. Успех — пять контрольных запросов возвращают ожидаемые поля, а сохранённая карточка открывается после отключения сети.
2. Прототип рекомендаций: локальный набор не менее 50 фильмов и три профиля — без оценок, с предпочтением фантастики, с отрицательными оценками жанра. Успех — просмотренные исключены, холодный старт не пуст, объяснения соответствуют входным данным.

Результат прототипа может привести к уточнению требований, но не считается готовой эксплуатационной реализацией.

#### 3.5.10 Управление изменениями

Изменения классифицируются:

- исправление — устраняет неоднозначность без изменения наблюдаемого поведения;
- дополнение — добавляет совместимую функцию;
- ломающий запрос — меняет существующий сценарий, данные или контракт;
- перенос — исключает требование из текущего выпуска без окончательного удаления.

Рабочий процесс:

1. Заказчик или владелец продукта формулирует замечание в pull request.
2. Автор связывает его с бизнес-целью и затронутыми требованиями.
3. Оцениваются трудоёмкость, срок, риск и влияние на макеты.
4. Решение фиксируется как «принято», «принято с изменением», «отложено» или «отклонено».
5. Для принятого изменения обновляются SRS, графические материалы и история изменений.
6. Изменение фиксируется отдельным коммитом и повторно направляется на ревью.

Отклонённое замечание не удаляется из обсуждения. Причина должна быть проверяемой: противоречие бизнес-цели, выход за границы, дублирование или несоразмерная стоимость.

### 3.6 ИИ/МО

MVP не использует обучаемую модель. Рекомендации формируются детерминированными правилами по жанрам, оценкам и статусам. Раздел заполнен, чтобы явно установить границы и требования к возможному будущему ML-компоненту.

#### 3.6.1 Спецификация модели

В MVP применяется версионируемый алгоритм ранжирования, а не ML-модель. Входы: жанры фильма, оценки текущего пользователя, статусы и общая популярность локального каталога. Выход: упорядоченный список и причины. Равные результаты разрешаются стабильным вторичным порядком, чтобы одинаковые данные давали воспроизводимую выдачу.

| ID | Требование | Критерий |
|---|---|---|
| REQ-ML-001 | Версия алгоритма должна фиксироваться с результатом диагностического прогона | Протокол содержит версию и входной набор |
| REQ-ML-002 | Одинаковые входные данные и версия должны давать одинаковый порядок | Два запуска совпадают |
| REQ-ML-003 | Внедрение ML требует новой версии SRS и критериев качества | В MVP отсутствует скрытая обучаемая модель |

#### 3.6.2 Управление данными

Для расчёта используются только данные текущего пользователя и общие метаданные каталога. Личные оценки разных пользователей не объединяются в обучающий набор. Тестовые наборы содержат вымышленные идентификаторы. Происхождение общих метаданных сохраняется через внешний идентификатор и источник.

| ID | Требование | Критерий |
|---|---|---|
| REQ-ML-004 | Личные заметки не должны использоваться как вход рекомендаций MVP | Тест изменения заметки не меняет выдачу |
| REQ-ML-005 | Экспорт тестовых данных не должен содержать email реального пользователя | Инспекция набора подтверждает псевдонимизацию |

#### 3.6.3 Ограничители (Guardrails)

Перед ранжированием система исключает неактивные карточки, просмотренные и брошенные фильмы. Оценки вне диапазона отклоняются до расчёта. Результат ограничивается десятью уникальными карточками. При невозможности вычислить персональный профиль используется явно обозначенный холодный старт.

| ID | Требование | Критерий |
|---|---|---|
| REQ-ML-006 | Просмотренные и брошенные фильмы не должны попадать в подборку | Контрольный набор даёт ноль нарушений |
| REQ-ML-007 | При ошибке алгоритма система должна показать нейтральный общий список или понятную ошибку | Страница не содержит частично повреждённые карточки |

#### 3.6.4 Этика

Система не утверждает, что рекомендация объективно определяет качество фильма. Пользователь видит основание и может игнорировать предложение. Демографические признаки, здоровье, религия и политические взгляды не собираются для подбора. Возрастные ограничения фильма могут отображаться как метаданные, но MVP не выполняет родительский контроль.

| ID | Требование | Критерий |
|---|---|---|
| REQ-ML-008 | Объяснение не должно содержать недоказанное утверждение о личности пользователя | Используются формулировки о жанрах и оценках |
| REQ-ML-009 | Чувствительные персональные признаки не должны входить в профиль | Модель данных и API не содержат таких полей |

#### 3.6.5 Human-in-the-Loop

Решение о просмотре всегда принимает пользователь. Он управляет оценками и статусами, которые влияют на следующий расчёт, и может удалить запись. Администратор может отключить ошибочную общую карточку, но не редактирует пользовательскую оценку.

| ID | Требование | Критерий |
|---|---|---|
| REQ-ML-010 | Рекомендация не должна автоматически менять личную коллекцию | До явного действия статус отсутствует |
| REQ-ML-011 | Пользователь должен иметь возможность исправить влияющую оценку | После изменения подборка пересчитывается по новым данным |

#### 3.6.6 Жизненный цикл модели и операции

Правила ранжирования хранятся в системе контроля версий. Для каждой версии выполняется постоянный набор сценариев: холодный старт, предпочтение жанра, отрицательная оценка, исключение просмотренного, стабильность результата. Предыдущая версия должна оставаться доступной в Git для анализа регрессии. Переход на ML требует отдельного набора данных, метрик, мониторинга дрейфа, процедуры отката и согласия владельца продукта.

### 5.3 Основные потоки

#### UC-01 Добавление фильма в план

1. Пользователь открывает каталог.
2. Вводит часть названия или применяет фильтры.
3. Система показывает подходящие карточки.
4. Пользователь нажимает «Хочу посмотреть».
5. Система создаёт или обновляет личную запись.
6. Карточка показывает новый статус.

Альтернативы: если пользователь не вошёл, система предлагает войти; если карточка отключена между поиском и сохранением, операция отклоняется с объяснением; повторное действие не создаёт дубль.

#### UC-02 Фиксация просмотра

1. Пользователь открывает фильм из каталога или коллекции.
2. Выбирает «Просмотрен».
3. Указывает дату, оценку и необязательную заметку.
4. Система проверяет значения.
5. При успехе система сохраняет запись и обновляет персональный профиль.

Альтернативы: неверная дата или оценка отмечается рядом с полем; ранее введённые допустимые значения остаются в форме.

#### UC-03 Получение рекомендаций

1. Пользователь открывает раздел рекомендаций.
2. Система получает его статусы и оценки.
3. Система исключает запрещённые карточки.
4. Система вычисляет и сортирует кандидатов.
5. Пользователь видит до 10 фильмов с причинами.
6. Пользователь сохраняет фильм либо открывает подробности.

Альтернатива: при недостатке оценок используется общий набор и показывается причина холодного старта.

### 5.4 Логическая модель данных

| Сущность | Ключевые поля | Связи |
|---|---|---|
| User | id, email, passwordHash, displayName, role, createdAt | Имеет много CollectionEntry |
| Movie | id, source, externalId, title, originalTitle, year, overview, active | Имеет жанры и много CollectionEntry |
| Genre | id, name, externalId | Связан со многими Movie |
| CollectionEntry | id, userId, movieId, status, watchedDate, rating, note, updatedAt | Принадлежит User и Movie |
| RecommendationSnapshot | id, userId, algorithmVersion, createdAt | Имеет элементы снимка при необходимости аудита |
| SyncRun | id, startedAt, finishedAt, status, updatedCount, errorSummary | Описывает синхронизацию каталога |

Ограничения данных: уникальность email без учёта регистра; уникальность пары userId–movieId; рейтинг 1–10; заметка не более 2000 символов; внешний идентификатор уникален в пределах источника.
